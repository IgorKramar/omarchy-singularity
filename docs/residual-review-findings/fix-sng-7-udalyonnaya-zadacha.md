# Что нашли и осознанно не чинили в SNG-7

Ревью плана пятью линзами (до кода) и ревью кода четырьмя, плюс три линзы упрощения.
Применено восемь замечаний по коду и шесть по плану; ниже — названное и оставленное.

## 1. Падающий запрос проектов повторяется каждый опрос, а не раз в сутки

Ключ суток теперь пишется только при успехе. Значит если `/v2/project` отказывает
постоянно, запрос уходит каждые десять минут — 2815 байт и ещё один круг до сервера, — и
каждый раз меняет `errorText`, а вместе с ним гасит тихий гейт: попап перестраивается на
каждом опросе, пока эндпоинт лежит.

**Почему не чиним.** Это осознанный размен, а не дефект. Раньше при отказе проектов ключ
всё равно проставлялся, и имена не появлялись **до следующих суток** — расхождение, ровно
однотипное тому, которое чинит эта задача. Повтор раз в десять минут восстанавливает имена
сам, как только эндпоинт оживёт.

Правильная починка — своё свойство ошибки у проектов, как уже сделано у пути записи
(`mutationError`), плюс подача его в подвал отдельной строкой. Это заметная работа в
интерфейсе и заслуживает своей задачи.

## 2. Тихий гейт на опросе больше не берёт быстрый путь

`sameTasks` сравнивает сперва по ссылке, потом по значению. У `merge` ссылки переживают
слияние через Map, поэтому отклик записи сериализует одну задачу. `mergeFull` строит набор
из свежих объектов `normalizeTask`, и совпадений по ссылке нет ни одного — сериализуется всё
окно, на каждом опросе, а не раз в сутки, как было.

**Почему не чиним.** Механизм назван верно, величина измерена: **0,13 мс** на окне из 103
задач и **0,11 мс** при заметке в 600 символов у каждой — против 655–766 мс сети. Это три
сотых процента.

Порог пересмотра: если окно вырастет на порядок (тысяча задач с заданным началом),
сравнение станет заметным. Готовая замена — сравнивать пару `(id, modifiedAt)` вместо
полной сериализации: сервер метит любое изменение полем `modificatedDate`, и оно уже
доезжает в нормализованную задачу.

## 3. Усечение ответа теперь стирает задачи, а не просто их не обновляет

`maxCount` равен 1000. Раньше усечённый ответ в инкременте означал «часть изменений не
приехала»; теперь полная выборка заменяет кэш целиком, и усечение означает «задач больше
нет». Единственный сигнал — предупреждение в журнал.

**Почему не чиним.** Окно на живом аккаунте — 103 задачи при замере и 3 в обычный день,
запас десятикратный. Достижимо только при тысяче задач с началом не позже сегодняшнего дня.
Если это станет возможным, усечение должно перестать быть предупреждением и стать видимым
состоянием — но это разговор о поведении, а не строка кода.

## 4. У API есть ограничение частоты, и плагин о нём не знает

Обнаружено при уборке замера: сто удалений подряд получили **HTTP 429**. Плагин покажет это
обычной ошибкой записи («Не сохранено») и повторять не станет.

**Почему не чиним.** В обычной работе недостижимо: пользователь не делает сотню записей в
минуту, а опрос идёт раз в десять минут. Осмысленная реакция — отступ с повтором — требует
решения о том, сколько ждать и что показывать всё это время.

## 5. `mergeFull` не дедуплицирует по id

`merge` строит Map и потому схлопывает повторы; `mergeFull` фильтрует список как есть. Ответ,
содержащий одну задачу дважды, дал бы две строки.

**Почему не чиним.** Ни одного случая дублей от этого API не наблюдалось, а Map ради
гипотетического дефекта сервера вернул бы в горячий путь аллокацию, которую эта задача
оттуда убрала.

## 6. Общий хвост `merge` и `mergeFull` не извлечён

Обе функции заканчиваются одинаково: `filter(isCurrent)` → `sort(byStartThenTitle)` →
вернуть прежнюю ссылку, если содержимое совпало.

**Почему не чиним.** Извлечение спрятало бы тихий гейт за третьим именем, которое его не
называет, ради четырёх строк. Обе функции читаются целиком за один взгляд; линза
повторного использования сама оценила находку как «на усмотрение».

## Проверено фактом и оказалось не находкой

- **Согласованность чтения после записи.** Состязательная линза предполагала, что опрос,
  начатый сразу после записи, может не увидеть её результат, и тогда задача исчезнет из
  окна до следующего опроса. Проверено на живом API: созданная задача видна следующим же
  запросом, отмеченная сразу уходит из выборки. Опасение снято.
- **Перенос признака «просили» через отброшенный отклик.** Шаг 6 плана требовал переносить
  `projectsFetchPending`, если отклик опроса отброшен как устаревший. После правки признак
  снимается только в успешной ветке проектов, поэтому переносить нечего — он и так
  переживает отбрасывание.
