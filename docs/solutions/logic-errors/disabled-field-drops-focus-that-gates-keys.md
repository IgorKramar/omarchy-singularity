# Выключенное поле отдаёт фокус — и уносит с собой блокировку клавиш, которая на этом фокусе держалась

## Проблема

Поле ввода выключалось на время отправки (`enabled: !sending`), чтобы пользователь не отправил его содержимое дважды. Выключение элемента в Qt Quick снимает с него активный фокус. А блокировка клавиатурного перехватчика — свойство, решающее, кому достаются клавиши, — была завязана на наличие фокуса у поля.

Получилось состояние, которое существует ровно на время запроса и разрушается по-разному в зависимости от того, как именно записана блокировка.

## Симптомы

Два лица одной ошибки, противоположные по виду:

**Поле добавления.** `blocked: addField.activeFocus`. Отправка → поле выключено → фокуса нет → блокировка падает → перехватчик снова считает клавиши командами списка. Пользователь, нажавший пробел сразу после Enter, **отмечает выполненной задачу под курсором**. Он этого не хотел и, скорее всего, не поймёт, что произошло: отмеченная задача исчезает из окна.

**Поле переименования.** `blocked: renamingId !== ""` — по состоянию панели, не по фокусу. Отправка → поле выключено → фокуса нет **ни у кого**, а блокировка поднята. Перехватчик пропускает клавиши насквозь, принять их некому. Клавиатура попапа мертва до конца запроса.

Оба длятся около 550 мс — столько идёт круг до API. На снимке экрана исправное и сломанное состояние не различаются.

## Что не сработало

Проверка глазами. Оба состояния короче, чем время между нажатием и взглядом на экран, и ни одно не оставляет следа: список не меняется, ошибок нет, в журнале пусто. Первое лицо ошибки (`Space` отмечает чужую задачу) внешне выглядит как случайное нажатие пользователя.

Автоматические проверки тоже молчат по устройству проекта: решение живёт в QML, а `node --test` до QML не достаёт.

Нашла ошибку линза корректности при ревью — чтением, а не прогоном, и сразу назвала общий корень для обоих симптомов.

## Решение

`readOnly` вместо `enabled: false`. Поле остаётся сфокусированным и по-прежнему не принимает ввод:

```qml
// было
enabled: !root.sending

// стало
enabled: root.svc && root.svc.apiToken !== ""   // это про право писать вообще
readOnly: root.sending                          // а это про «сейчас идёт запрос»
```

Плюс защита от повторной отправки там, где поле остаётся живым и может принять Enter второй раз:

```qml
onAccepted: if (!root.renameSending) root.renameAccepted(text)
```

и симметрично в обработчике панели:

```qml
function submitAdd() {
  if (!root.svc || root.addSending) return
  ...
}
```

## Почему это работает

`enabled` отвечает на вопрос «участвует ли элемент во взаимодействии вообще» и потому трогает фокус. `readOnly` отвечает на вопрос «принимает ли он ввод прямо сейчас» и фокуса не касается. Состояние «запрос в пути» — это второй вопрос, а не первый.

Общее правило шире этого случая: **всё, что рассуждает о фокусе, ломается о выключение элемента.** Если какое-то состояние интерфейса вычисляется из `activeFocus`, то любой путь, снимающий фокус — `enabled: false`, удаление элемента, перестроение списка, — меняет это состояние молча и в момент, который никто не выбирал.

## Профилактика

- **Ищите пары «выключается» и «читает фокус».** Если элемент когда-либо выключается, а что-то рядом читает его `activeFocus`, — это та же ошибка, как бы она ни выглядела снаружи.
- **Состояние «идёт запрос» выражайте свойством, не отключением.** `readOnly`, `busy`, отдельный признак — что угодно, что не трогает фокус.
- **Блокировка перехватчика должна опираться на состояние владельца, а не на фокус получателя** — но и тогда проверьте, что при поднятой блокировке есть кому принимать клавиши. Поднятая блокировка без фокуса означает захваченную клавиатуру: перехватчик клавиши только пропускает, и принять их некому.
- **Проверять руками бесполезно** — состояние короче взгляда. Ловится чтением: где фокус может исчезнуть, и что об этом думает всё, что от фокуса зависит.

Смежное по форме: [окно задач фильтруется на клиенте, и у предиката один владелец](../design-patterns/incremental-sync-window-filter-on-client.md). Там правило собрано в одном месте намеренно; здесь ошибка в том, что состояние вычислялось из свойства, которое меняет кто-то третий.
