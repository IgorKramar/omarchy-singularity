# Решение о равенстве принимает тот, кто строит значение, — и живёт оно там, куда дотягивается тест

## Problem

В плагине ровно одна граница, через которую не проходит ни один автоматический прогон: `Api.mjs` — чистый ES-модуль без Qt, его импортируют и `Service.qml` (`import "Api.mjs" as Api`, `Service.qml:4`), и `node --test`; QML тестовый раннер не видит вообще. Проверка в CI названа файлом явно — `node --test test/api.test.mjs` (`.github/workflows/ci.yml:24`), и до `Service.qml` она не доходит по устройству, а не по недосмотру.

SNG-1 завела вокруг этой границы **тихий гейт**: `merge()` при неизменном опросе возвращает **ту же ссылку** на массив (`Api.mjs:125`), а сервис по этой ссылке решает, испускать ли `changed()` (`Service.qml:191`). Гейт существует затем, чтобы поверхность, связанная с набором, не перестраивалась на каждом тике опроса, а опрос идёт постоянно и почти всегда вхолостую.

SNG-2 добавила отсев проектов. `applyProjectFilter` ссылку тоже сохраняет — но только на путях, где ничего не выброшено: пустой список исключаемых (`Api.mjs:156`), ни одно название не разрешилось в проект (`Api.mjs:160`), отсев прошёл вхолостую (`Api.mjs:162`). Как только он **действительно что-то выбрасывает**, `.filter()` строит новый массив, и делает это заново на каждом вызове. Решение о равенстве при этом осталось в QML: `recompute()` в версии PR #2 сравнивал `next === root.tasks` сам.

Итог: у каждого, кто настроил фильтр — то есть ради кого фича и делалась, — проверка не могла стать истинной никогда, и `changed()` срабатывал на каждом опросе. Гейт, ради которого SNG-1 писала возврат той же ссылки, умирал ровно там, где начиналась польза от SNG-2.

## Symptoms

**Чем это было невидимо** — важнее самого дефекта:

- **22 юнита зелёные.** Три утверждения про сохранение ссылки в тестах PR #2 (в текущем файле те же утверждения стоят на `test/api.test.mjs:177`, `:181–182`, `:197`) все три легли на **ранние возвраты** `applyProjectFilter`: пустой список, неизвестное название, пустой кэш проектов. Путь отбрасывания — единственный, на котором ссылка меняется, — не проверялся ни разу. Тесты утверждали свойство ровно там, где оно выполняется тривиально.
- **`bash test/omarchy-plugin-validate` проходил, джоб `check` зелёный.** Оба смотрят на манифест и на модуль, ни один — на шесть строк в QML.
- **Фича работала.** Число в баре менялось при правке `shell.json`, счётчики считались верно. Дефект не в результате, а в частоте его публикации: лишний `changed()` не искажает ни одного значения.
- **План это предсказал и был нарушен молча.** KTD5 (`docs/plans/2026-09-03-002-feat-sng-2-pilyulya-plan.md:149`) требовал, чтобы логика отсева и подсчёта жила в `Api.mjs` чистыми функциями, «потому что в QML эта логика не покрывается `node --test`». Шесть строк, оставшиеся в `recompute()`, и были отступлением от KTD5 — и именно они содержали решение, ошибка в котором не ловится ничем.

Нашло это ревью кода шестью линзами. По записи в `docs/residual-review-findings/feat-sng-2-pilyulya.md` пять линз из шести пришли к одному и тому же независимо, с воспроизведением на настоящем `Api.mjs`. **Ревью плана, шедшее перед реализацией, дефект не поймало** — на уровне плана KTD5 выглядел соблюдённым. Не поймал и ни один тест.

## What Didn't Work

Дефект не был найден ничем из того, что для этого существует.

- **Ревью плана перед реализацией.** На уровне плана KTD5 выглядел соблюдённым: логика отсева и подсчёта действительно уехала в `Api.mjs`. Отступлением были шесть строк склейки в `recompute()`, которых в плане нет и быть не может — план не описывает, где стоит сравнение.
- **Тесты.** Прогон зелёный и до, и после появления дефекта. Утверждения о ссылочной стабильности стояли там, где свойство выполняется тривиально.
- **Ручная проверка.** У проверяющего фильтр не настроен, а без фильтра гейт держится — конфигурация разработчика ровно та, в которой дефекта нет.
- **Валидатор и CI.** Оба смотрят на манифест и на модуль; шесть строк в QML им структурно недоступны.

Сработало ревью кода шестью линзами: пять из шести пришли к одному и тому же независимо, с воспроизведением на настоящем `Api.mjs`.

## Solution

**Ссылочная стабильность — это контракт производителя значения, а не соглашение вызывающего.** Функция, чей результат используют для сравнения «изменилось ли», обязана сама решить вопрос равенства и сама вернуть прежнюю ссылку. Вызывающему нельзя оставлять `a === b`: он не видит, по скольким путям производитель аллоцирует.

Практически:

1. **Сравнение живёт рядом с построением.** Если вид собирается из нескольких шагов, чистой должна быть не каждая ступенька по отдельности, а **вся композиция целиком** — вместе с ответом «считать ли это изменением».
2. **Схлопывание на предыдущее значение — часть возврата.** Функция принимает `prev` и, получив содержательно тот же результат, отдаёт обратно именно `prev`.
3. **Вид равенства выбирается по происхождению данных.** `merge` сравнивает содержимое (`sameTasks`, `Api.mjs:128–130`), потому что элементы приходят из разбора ответа и объекты каждый раз новые. `computeView` сравнивает по идентичности элементов (`sameOrder`, `Api.mjs:175–177`), потому что оба массива держат те самые объекты, которые в кэш положил `merge`.
4. **Граница тестируемости — это проектное ограничение, а не деталь оформления.** В QML остаётся присваивание и сравнение скаляров. Любое решение, ошибка в котором молчалива, уезжает за границу до того, как код написан, а не после того, как ревью его нашло.

Так и починено в PR #3 — не заплаткой в сравнении, а переносом всего вычисления вида в `Api.mjs`:

```js
// Api.mjs:175-177, 184-193
function sameOrder(a, b) {
  return a.length === b.length && a.every((t, i) => t === b[i])
}

export function computeView(prev, allTasks, projects, excluded, now) {
  const names = normalizeExcluded(excluded)
  const applied = names.size === 0 || projects.length > 0
  let tasks = applied ? applyProjectFilter(allTasks, projects, excluded) : allTasks
  if (tasks !== prev && sameOrder(prev, tasks)) tasks = prev
  const { total, overdue } = countWindow(tasks, now)
  return { tasks, total, overdue, applied, excludedCount: names.size }
}
```

`recompute()` в `Service.qml:95–109` сравнение по ссылке **не потерял** — строка `view.tasks === root.tasks` (`Service.qml:98`) на месте. Изменилось другое: теперь эта проверка **может стать истинной**, потому что гарантию даёт производитель. Вызывающий не угадывает свойство — он им пользуется.

## Why This Works

Класс ошибки узнаётся по трём признакам сразу, и ни один из них не выглядит тревожным:

- **все проверки зелёные**;
- **фича демонстрируемо работает**;
- **вред — в частоте события, а не в значении**, поэтому его нельзя увидеть ни на скриншоте, ни в утверждении о содержимом.

Единственное место, где дефект был бы виден заранее, — это вопрос «на каком пути свойство ссылки нарушается и есть ли на нём тест», а не «проходят ли тесты». Три утверждения, покрывавшие ранние возвраты, читались как покрытие свойства, хотя доказывали его только там, где оно бесплатно. Отсюда общее: **утверждение о ссылочной стабильности имеет смысл только на пути, где функция аллоцирует.** Тест на пути раннего возврата почти всегда ложное покрытие.

Второе следствие касается границы. Асимметрия «модуль тестируется, QML не тестируется вовсе» превращает вопрос «где живёт эта строка» в вопрос «проверяется ли она когда-нибудь». Шесть строк в `recompute()` не были ни ленью, ни срезанным углом — они выглядели как естественное место для склейки. Пока граница не названа вслух правилом уровня плана (а KTD5 её называл), она соблюдается по ощущению, и отступление от неё не оставляет следа: диффа «нарушено KTD5» не бывает.

Родственная запись — [`incremental-sync-window-filter-on-client.md`](../design-patterns/incremental-sync-window-filter-on-client.md): там окно применялось на клиенте, потому что владелец предиката должен быть один. Здесь тот же принцип единственного владельца применён не к предикату окна, а к решению о равенстве. Разница в том, что ту ошибку поймало ревью плана — оно смотрело на то, чего сервер **не** пришлёт. Эту ревью плана не поймало: она видна только на уровне того, какая функция какую ссылку вернёт.

## Prevention

- Любой кэш или вид, у которого есть **тихий гейт**: сигнал/notify/ре-рендер испускается только при фактическом изменении, а «фактическое» определяется через `===`.
- Как только между источником и гейтом появляется **ещё один шаг** — отсев, сортировка, проекция, — и этот шаг иногда аллоцирует, а иногда нет.
- Всюду, где часть кода **структурно недостижима для тестового раннера**: QML при `node --test`, шаблоны, шейдеры, конфигурация, склейка в фреймворке. Правило простое: за такой границей остаётся присваивание и сравнение скаляров, но не решение, ошибка в котором молчит.
- При чтении тестов на ссылочную стабильность — сверять, **на каком именно пути** функции стоит каждое утверждение.

Было (PR #2, `Service.qml`, вырезано целиком) — равенство решает вызывающий:

```qml
function recompute() {
  var wanted = Api.normalizeExcluded(root.excludedProjects).size > 0
  var applied = !wanted || root.projects.length > 0
  var next = applied
    ? Api.applyProjectFilter(root.allTasks, root.projects, root.excludedProjects)
    : root.allTasks
  var counts = Api.countWindow(next, new Date())
  var same = next === root.tasks           // ← у настроившего фильтр никогда не true
    && counts.total === root.visibleCount
    && counts.overdue === root.overdueCount
    && applied === root.filterApplied
  root.tasks = next
  ...
  return !same
}
```

Стало (PR #3, `Service.qml:95–109`) — присваивание и сравнение скаляров:

```qml
function recompute() {
  var view = Api.computeView(root.tasks, root.allTasks, root.projects,
                             root.excludedProjects, new Date())
  var same = view.tasks === root.tasks
    && view.total === root.visibleCount
    && view.overdue === root.overdueCount
    && view.applied === root.filterApplied
    && view.excludedCount === root.excludedCount
  root.tasks = view.tasks
  ...
  return !same
}
```

Воспроизведение (прогон на настоящем `Api.mjs`, три подряд пересчёта неизменного окна; после починки четыре):

```
до починки, фильтр задан:    changed, changed, changed
до починки, фильтра нет:     changed, quiet, quiet
после починки, фильтр задан: changed, quiet, quiet, quiet
после починки, фильтра нет:  changed, quiet, quiet, quiet
```

Вторая строка и есть причина невидимости: без фильтра — то есть в конфигурации разработчика и в большинстве ручных проверок — гейт держался.

Тесты выросли с 22 до 32. Два из новых закрывают именно ту дыру, в которую провалились прежние три:

```js
// test/api.test.mjs — путь отбрасывания, где ссылка обязана меняться
test("отсев на пути отбрасывания строит новый массив каждый вызов — сравнивать по ссылке нельзя", () => {
  const first = applyProjectFilter(window8, projects, ["Дни рождения"])
  const second = applyProjectFilter(window8, projects, ["Дни рождения"])
  assert.notEqual(first, second, "это и есть контракт, под который обязан подстраиваться вызывающий")
  assert.deepEqual(first.map((t) => t.id), second.map((t) => t.id))
})

// повторный вызов на неизменном окне: ссылка обязана устояться
test("computeView: повторный вызов на неизменном окне возвращает прежнюю ссылку — гейт держится", () => {
  let view = computeView([], window8, projects, ["Дни рождения"], now)
  // …
  const settled = view.tasks
  for (let i = 0; i < 3; i++) {
    view = computeView(view.tasks, window8, projects, ["Дни рождения"], now)
    assert.equal(view.tasks, settled, "тихий опрос не должен подменять ссылку")
  }
})
```

Первый закрепляет контракт «здесь ссылка меняется всегда» как факт, к которому обязан приспособиться вызывающий; второй проверяет само устаканивание — свойство, которое до PR #3 не проверял никто, потому что проверять его было негде.

### Правильного места мало — важен ещё и состав сравнения (дополнено 04.09.2026)

Четыре пункта выше верны, но исчерпывающим чек-листом для тихого гейта не являются. SNG-3
показала второй способ сломать тот же механизм: решение о равенстве стояло уже в чистой
функции, было покрыто тестами — и всё равно было неверным, потому что **список полей,
которые оно сравнивает, ведётся руками и молча расходится со списком полей, которые читает
потребитель**. `sameGroups` не сравнивала `title`, и переименованный проект держал старое
имя до конца сессии.

Пятый пункт к списку: **состав сравнения — это отдельный контракт с потребителем**, и
компилятор его не проверяет. Каждое новое поле, которое кто-то начинает рисовать, обязано
попасть в сравнение, а тест должен варьировать **каждое поле по отдельности** — «один тест
на функцию» не то же самое, что «один тест на поле».

Разбор — [`quiet-gate-field-list-comparison-omits-title.md`](./quiet-gate-field-list-comparison-omits-title.md).
